Why another supply-chain scanner

Most tools tell you about malware after someone else already found it. MalwHunter is built to catch what nobody's seen yet.

Reputation-based scanning

npm audit, Socket.dev, Snyk — all mostly match a dependency against a database of already-known bad packages. Useful, but a brand-new malicious package published an hour ago sails straight through.

Pattern-matching alone

Regex can flag a suspicious-looking blob, but it can't decode and judge one. A base64-encoded payload that unpacks to a credential-harvesting shell command is invisible to pure static analysis.

MalwHunter's bet

Combine static pattern-hunting with an actual sandboxed detonation pass. Catch malicious behavior, not just malicious reputation — works even against something nobody has ever seen before.

No observation, no verdict

Enforced in code — a Signal cannot exist without evidence attached. Every result traces back to a specific file, line, network destination, or decoded payload.

How it works

Two independent passes feed one artifact — the Dossier, one per exact package@version, cacheable across every project that depends on it.

CLI reference

CommandWhat it does
malwhunter scan .Resolve the project's package.json/lockfile and hunt every dependency.
malwhunter scan . --no-detonateRecon + Analyst only — no Docker needed, much faster.
malwhunter inspect <name>@<version>Deep-dive a single package.
--format json|markdown|terminalOutput format — terminal is colorized ANSI.
--fail-on malicious|suspicious|noneExit 1 if any package reaches this verdict level or worse (default: malicious).
--ai / --no-aiEnable/disable the Analyst. Falls back automatically if claude isn't on PATH.

Architecture

One Dossier model, two independent detection passes, a narrow AI layer used only where pattern-matching structurally can't reach.

malwhunter/
├─ intake/      # package.json/lockfile parsing, npm registry fetch, safe tarball extraction
├─ recon/       # the static signal catalog — regex/entropy heuristics
├─ chamber/     # Docker orchestration for the sandboxed Detonation run
├─ wiretap/     # the recording proxy + canary/tripwire injection
├─ analyst/     # the narrow AI-judgment layer — own prompts, own interface
├─ dossier/     # the Dossier/Signal/Verdict model — evidence is mandatory
├─ report/      # JSON / Markdown / terminal output
└─ cli.py          # `malwhunter scan` / `malwhunter inspect`

Status & roadmap

Early and under active development.

Built & live-verified

  • Recon's full catalog, real npm registry fetch, path-traversal-safe extraction
  • The Analyst's two-pass second opinion — proven live against a base64-encoded RCE payload regex alone can't decode
  • Deterministic verdict combination
  • JSON / Markdown / colorized terminal reporting

Built, not yet live-verified / not started

  • The Detonation sandbox's full chain (container → proxy → tripwire) — components are individually tested, the end-to-end run needs Docker running to confirm
  • Ecosystems beyond npm (PyPI is structurally different)
  • Runtime instrumentation beyond install-lifecycle scripts
  • Package reputation/history signals, a CI watch mode
