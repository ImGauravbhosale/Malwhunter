Why another supply-chain scanner

Most tools tell you about malware after someone else already found it. MalwHunter is built to catch what nobody's seen yet.

Reputation-based scanning

npm audit, Socket.dev, Snyk — all mostly match a dependency against a database of already-known bad packages. Useful, but a brand-new malicious package published an hour ago sails straight through.

Pattern-matching alone

Regex can flag a suspicious-looking blob, but it can't decode and judge one. A base64-encoded payload that unpacks to a credential-harvesting shell command is invisible to pure static analysis.

MalwHunter's bet

Combine static pattern-hunting with an actual sandboxed detonation pass. Catch malicious behavior, not just malicious reputation — works even against something nobody has ever seen before.

No observation, no verdict

Enforced in code — a Signal cannot exist without evidence attached. Every result traces back to a specific file, line, network destination, or decoded payload.

Quick start

Three ways to check a package. Pick one, or combine them.

1. Static analysis

Reads the code and runs nothing. Fast, and needs no Docker.
--mode static

2. Detonation

Runs the install script in a locked-down sandbox and reports what it did: hosts contacted, files touched, secrets sent. Needs Docker.
--mode detonate-only or --mode full (both)

3. AI-agent review

Writes a brief you paste into Claude, ChatGPT or Gemini to check the findings yourself.
--format agent-prompt --out review.md

Not sure? Use the default

Static analysis on everything, sandbox only for packages that are new, obscure or already flagged.
--mode auto

git clone https://github.com/ImGauravbhosale/Malwhunter.git
cd Malwhunter && uv sync
uv run malwhunter                       # the logo and every command
uv run malwhunter scan . --mode static

How it works

Code reading and a sandbox run feed one artifact — the Dossier, one per exact package@version, cacheable across every project that depends on it.

Commands

Run malwhunter with no arguments to see this list in your terminal, with the logo.

On your machine

malwhunter scan . --mode static                  # read the code only (no Docker)
malwhunter scan . --mode detonate-only           # sandbox only (needs Docker)
malwhunter scan . --mode full                    # both, all in one
malwhunter inspect left-pad@1.3.0 --mode full    # one npm package
malwhunter inspect pypi:requests==2.31.0         # one PyPI package
malwhunter scan . --format agent-prompt --out review.md   # brief for an AI agent

In CI/CD

# Full scan: every dependency, nothing remembered between runs
malwhunter scan . --mode full --fail-on malicious --jobs 4 \
  --format json --out malwhunter-report.json

# Delta scan: only new or changed packages (keep the cache folder between runs)
malwhunter scan . --mode auto --fail-on malicious --jobs 4 \
  --cache-dir .malwhunter-cache --format json --out malwhunter-report.json

Options

OptionWhat it does
--mode static|detonate-only|full|autoWhat to run. auto is the default.
--format json|markdown|terminal|csv|sarif|agent-promptOutput format. csv is one row per finding for spreadsheets; sarif feeds GitHub code scanning; agent-prompt writes a review brief for any AI agent. Add --out FILE to save it.
--fail-on malicious|suspicious|noneExit 1 when a package reaches this level or worse (default: malicious).
--cache-dir DIRRemember results so the next scan only checks new or changed packages.
--jobs NCheck N packages at once (the sandbox still runs one at a time).
--aiOptional: ask your own claude CLI for a second opinion on encoded strings. Off by default.

Exit code: 0 nothing found · 1 findings at your --fail-on level · 2 some package could not be scanned.

Architecture

One Dossier model, two detection passes (code and sandbox), and a narrow AI layer used only where pattern-matching structurally can't reach.

malwhunter/
├─ intake/      # npm + PyPI: lockfiles, registry fetch, checked downloads, safe unpacking
├─ recon/       # static analysis: JavaScript syntax trees, Python ast, the signal catalog
├─ chamber/     # the Docker sandbox: install runs, syscall trace, cleanup
├─ wiretap/     # recording proxy, HTTPS inspection, fake-secret tripwires
├─ analyst/     # the narrow AI second-opinion layer
├─ dossier/     # Dossier / Signal / Verdict: evidence is mandatory
├─ report/      # terminal, JSON, Markdown, CSV, SARIF, and the AI-agent review brief
├─ cache.py        # remembers results for delta scans
└─ cli.py          # `malwhunter scan` / `malwhunter inspect`, and the help screen

Limits

MalwHunter is a heuristic tool, not a guarantee. What it cannot see:

  • It checks install-time and import-time behavior, not what a package does later when you use it.
  • The sandbox watches for 30 seconds (120 for Python installs). A script that waits longer is not seen.
  • HTTPS is read through a certificate made for each run. A program that pins certificates only shows up as a connection attempt.
  • The syscall trace runs as the package's own user, so it is best-effort. Tampering is reported, and a host that blocks tracing is reported as unavailable, never as clean.
  • Static rules can be wrong. Use a reviewed .MHignore entry for a false positive.
  • npm needs package-lock.json (v2 or v3). For PyPI, one wheel per release is scanned.

Status

Active development. What works today, and what is next.

Built & tested

  • Static analysis of npm (syntax trees) and PyPI (ast) packages
  • Sandbox detonation of npm install scripts and pip install, with HTTPS inspection and a syscall trace, tested against real containers
  • Fake-secret tripwires: environment variables and fake ~/.ssh/id_rsa, ~/.aws/credentials, ~/.npmrc and ~/.pypirc files, caught even when re-encoded as base64, hex or URL-encoding
  • Four scan modes, delta scans, parallel jobs, JSON / Markdown / CSV / SARIF / terminal reports
  • AI-agent review brief (--format agent-prompt)
  • GitHub Action, .MHignore with reasons and expiry dates

Not started

  • Ecosystems beyond npm and PyPI
  • Behavior that only appears when a package is used, not installed or imported
  • A user-configurable verdict policy
  • A CI watch mode
  • Comparing a package with its earlier versions, and a DNS log inside the sandbox
  • Published benchmark numbers
